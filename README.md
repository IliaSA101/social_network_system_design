# Социальная сеть для путешественников — System Design

Учебный репозиторий по курсу [System Design](https://balun.courses/courses/system_design) (Balun-courses).

Социальная сеть для путешественников: публикация постов о поездках с фотографиями и привязкой к месту, реакции и комментарии, подписки, лента и поиск популярных мест.

---

## Функциональные требования

1. **Посты из путешествий:** 
	1.1. Публикация с фотографиями, небольшим описанием;
	1.2. Привязка к конкретному месту путешествия; 
	1.3. Оценки постов — 1–5 звёзд; 
	1.4. Комментарии к постам.
2. **Подписка** на других путешественников.
3. **Лента** постов, на которых мы подписаны, в обратном хронологическом порядке.
4. **Просмотр лент других пользователей** — только их постов.
5. **Поиск популярных мест** для путешествий и просмотр постов с этих мест.

### Вне скоупа

- Оповещения;
- Авторизация;
- Страница профиля;
- Модерация;
- Редактирование и удаление постов.

### Допущения

1. Привязка к конкретному месту путешествия — это координаты для расчёта трафика (привязка и выбор из внешнего сервиса карт в браузере);
2. Просмотр лент других пользователей — выглядит точно так же, как собственная лента, с фильтром на посты пользователя;
3. Поиск популярных мест для путешествий и просмотр постов с этих мест: геометрия из групп координат — получение средней, запрос местоположения для обратного геокодирования, с привязкой к постам. 2 вида представления поиска (представление разное, но выдача данных почти одинаковая): 
	3.1. Каталог с 2 уровнями вложенности с количеством постов (похожий вид на ленту) — далее лента с постами из этого места;
	3.2. Карта (внешний сервис) с точками 1-го уровня каталога, при большем приближении 2-й уровень каталога — переход в ленту с постами из этого места.
4. Из-за допущений 2 и 3 расчёт лент будет смешан в средних значениях по пользователю, хотя их выдача будет по факту стоить по-разному.
5. Обложка поста в ленте — сжатое фото 100 КБ; в карточке поста отдаётся полноразмерное фото до 500 КБ.
6. Фото грузятся lazy: в среднем просматривается половина карточки (5 фото из 10) и 80% страницы ленты (16 фото из 20).
7. Фото при публикации загружаются отдельными запросами, по 1 в секунду асинхронно.
8. Пользователь как сущность в системе существует (автор поста, стороны подписки), за скобки вынесены только механика авторизации и страница профиля.
9. Место идентифицируется geohash-префиксом, вычисляемым из координат поста: 4 символа — 1-й уровень каталога, 6 символов — 2-й. Название берётся обратным геокодированием центра ячейки. Собственного справочника мест нет, дерево не хранится — иерархия задаётся длиной префикса.
10. Место попадает в каталог автоматически, по порогу количества постов в ячейке: меньший порог выводит место на 2-й уровень, больший — на 1-й. Обложка места — фото из поста этой ячейки, описания мест не ведутся.
11. Оценка места — агрегат оценок постов ячейки, отдаётся вместе с количеством постов.

## Нефункциональные требования

### Аудитория приложения

**Количество пользователей**

- 10 000 000 DAU, дальше продолжает расти.

**Поведение пользователей** (значения ниже — мои допущения на основе инженерного опыта и порядков величин в существующих соцсетях.)

Один пользователь в среднем будет:

- делать 1 пост в месяц:
    - 1500 символов текста в посте;
    - 10 фото;
- оставлять 3 комментария в день, 150 символов в комментарии;
- подписан на 200 путешественников;
- просматривать ленту 10 раз в день (по 1 странице; может несколько страниц своей, может чужих, может поисковую);
- производить 1 поиск в неделю, с 7 переходами по каталогу в ленты популярных мест;
- производить 1 подписку в день;
- ставить 10 оценок в день.

Дополнительно:

- в ленте 1 сжатое фото (обложка) от поста — 100 КБ, и 100 символов;
- 5 комментариев под постом в среднем.

**Регионы использования приложения**

- Только СНГ.

### Особенности приложения

**Сезонности в приложении**

- Да, массовые периоды отпусков — в 3 раза большая активность, чем в среднем.
  Периоды: конец новогодних праздников (5–15 января), майские праздники (5–15 мая), август.

**Условия хранения данных**

- Храним всегда.

**Лимиты и ограничения**

- 20 фото на пост, фото не более 500 КБ;
- 4000 символов текста в посте;
- 500 символов в комментарии;
- 20 постов в ленте на страницу.

**Временные ограничения**

- Отрисовка 1-го экрана — 2 секунды.

**Доступность приложения**

- Не более нескольких часов простоя в год — 99,9%.

## Оценка нагрузки (примерная)

Допущение: в сутках 86 400 секунд — для счёта в уме берём 100 000.

Подсистемы выделены из функциональных требований: 
* Посты (ФТ 1.1, 1.2), 
* Изображения (фотографии из ФТ 1.1), 
* Реакции (ФТ 1.3), 
* Комментарии (ФТ 1.4), 
* Подписки (ФТ 2), 
* Поиск (ФТ 5). 
* Ленты (ФТ 3, 4), считаются как операции чтения внутри Постов и Изображений.
### Подсистема: Посты

#### Операция: Написание поста

RPS (запись):

```
DAU = 10 000 000
1 пост в 30 дней
RPS = 10 000 000 / (30 * 100 000) = 3
```

Трафик (запись):

```
RPS = 3
Без фотографий - за них другая подсистема отвечает, тут только URL;
Средний размер запроса =
	1500 символов текст * 2 байта = 3 КБ текст;
JSON обвязка:
	UUID пользователя - 36 байт;
	Дата - 20 байт;
	Координаты - 32 байта;
	+ идентификаторы, и еще доп. параметры;
Пусть 200 байт.
Итого 3,2 КБ
Traffic = 3,2 КБ * 3 = 10 КБ/с
```

#### Операция: Карточка поста

RPS (чтение):

```
DAU = 10 000 000
2 просмотра постов на 1 ленту (10 лент);
RPS = 10 000 000 * 10 * 2 / 100 000 = 2000
```

Трафик (чтение):

```
RPS = 2000
Средний размер запроса =
	Ссылки 10 фото, по 100 байт на 1 адрес с идентификатором = 1 КБ;
	Текст = 3 КБ (1500 символов);
	JSON обвязка 0,2 КБ;
Traffic = 4,2 КБ * 2000 = 8,4 МБ/с
```

#### Операция: Просмотр ленты

RPS (чтение):

```
DAU = 10 000 000
10 просмотров ленты;
RPS = 10 000 000 * 10 / 100 000 = 1000
```

Трафик (чтение):

```
RPS = 1000
Средний размер запроса =
	20 постов в ленте, это 20 url картинок = 2 КБ
	20 * 100 символов * 2 байта = 4 КБ
	Обвязка JSON к каждому посту по 200 байт * 20 = 4 КБ
Traffic = 1000 * 10 КБ = 10 МБ/с
```

### Подсистема: Поиск

Просмотр 1-2 уровня каталогов по сути сводится к аналогу ленты с меньшим RPS. Расчёт нужен для подсистемы «Изображения».

Выдача каталога устроена почти, как лента: та же страница на 20 элементов, только фото места вместо фото поста и название места вместо описания поста. Поэтому в подсистемах «Изображения» и «Реакции» эти 100 RPS считаются по ленточным нормам и складываются с лентой: 1000 + 100 = 1100.

Сами ленты мест сюда не входят — переход из каталога в ленту места это обычный просмотр ленты, он уже внутри 10 просмотров ленты в день (допущение 4: своя, чужая и поисковая лента смешаны в одном числе).

#### Операция: Просмотр каталога / карты

RPS (чтение):

```
DAU = 10 000 000
1 поиск в неделю, с 7 переходами по каталогу в ленты популярных мест
- фактически в среднем 1 лента в день на пользователя;
RPS = 10 000 000 * 1 / 100 000 = 100
```

Трафик (чтение):

```
RPS = 100
Средний размер запроса =
	20 разделов, подразделов на страницу: это 20 url картинок = 2 КБ
	Обвязка JSON к каждому разделу по 200 байт * 20 = 4 КБ
Traffic = 100 * 6 КБ = 0,6 МБ/с
```

### Подсистема: Изображения

#### Операция: Написание поста

RPS (запись):

```
3 RPS создания поста
	10 фото - загрузка по 1му в секунду асинхронно
3 * 10 = 30
```

Трафик (запись):

```
RPS = 30
	фото по 500 КБ, сжимается в браузере, количество в RPS учтено
Traffic = 500 КБ * 30 = 15 МБ/с
```

#### Операция: Карточка поста

RPS (чтение):

```
2000 RPS просмотра поста
10 фото * 0,5 - в среднем пользователи смотрят половину карточки, фото грузятся lazy
2000 * 5 = 10 000
```

Трафик (чтение):

```
RPS = 10000
Средний размер запроса = 1 фото 0,5 МБ в RPS уже число фото учтено
Traffic = 0,5 МБ * 10000 = 5 ГБ/с
```

#### Операция: Просмотр ленты (+ просмотр поисковой ленты)

RPS (чтение, посчитан ранее). Каталог поиска отдаёт такие же 20 обложек на страницу, что и лента (см. подсистему «Поиск»), поэтому его 100 RPS складываются с 1000 RPS ленты:

```
1000 + 100 = 1100 RPS просмотр лент
20 фото * 0,8 - в среднем пользователи смотрят 80% ленты, фото грузятся lazy
1100 * 16 = 17 600
```

Трафик (чтение):

```
RPS = 17 600
Средний размер запроса = 1 фото 0,1 МБ в RPS уже число фото учтено
Traffic = 17 600 * 0,1 МБ = 1,76 ГБ/с
```

### Подсистема: Комментарии

#### Операция: Оставление комментария

RPS (запись):

```
DAU = 10 000 000
3 комментария в день
RPS = 10 000 000 * 3 / 100 000 = 300
```

Трафик (запись):

```
RPS = 300
Средний размер запроса =
	Текст = 150 * 2 байта;
	Обвязка JSON 200 байт (ID кто, кому, дата)
Traffic = 0,5 КБ * 300 = 150 КБ/с
```

#### Операция: Карточка поста

RPS (чтение, посчитан ранее): 2000

Трафик (чтение):

```
RPS = 2000
	5 комментариев по 150 символов (300 байт текст + 200 байт JSON обвязка)
	в среднем под постом = 2,5 КБ;
Traffic = 2,5 КБ * 2000 = 5 МБ/с
```

### Подсистема: Реакции

#### Операция: Проставление оценки

RPS (запись):

```
DAU = 10 000 000
10 оценок в день
RPS = 10 000 000 * 10 / 100 000 = 1000
```

Трафик (запись):

```
RPS = 1000
Средний размер запроса =
	Обвязка + оценка JSON 200 байт (ID кто, кому, дата, оценка)
Traffic = 200 байт * 1000 = 200 КБ/с
```

#### Операция: Карточка поста

RPS (чтение, посчитан ранее): 2000

Трафик (чтение):

```
RPS = 2000
Средний размер запроса =
	Ср. значение самого поста 20 байт, по факту будет приходить с JSON поста;
Traffic = 20 * 2000 = 40 КБ/с
```

#### Операция: Просмотр ленты (+ просмотр поисковой ленты)

RPS (чтение, посчитан ранее): 1000 + 100 = 1100. Payload каталога по структуре повторяет ленту (см. подсистему «Поиск»), поэтому 100 RPS каталога сложены с 1000 RPS ленты.

Трафик (чтение):

```
RPS = 1100
Средний размер запроса =
	20 постов на 1 страницу по 10 байт (приходит с данными JSON поста),
	в итоге можно будет пренебречь = 200 байт
Traffic = 1100 * 200 байт = 220 КБ/с
```

### Подсистема: Подписки

#### Операция: Проставление подписки

RPS = 10 000 000 * 1 / 100 000 = 100

Трафик (запись):

## REST API

Спецификация OpenAPI 3.2 — [`api/rest_api.yml`](api/rest_api.yml).

Покрывает функциональные требования выше: публикация поста с фотографиями
и привязкой к месту, комментарии, оценки, подписки, лента и каталог мест.

**Решения по контракту:**

- Пагинация всех списков курсорная. Offset и номер страницы отброшены: при
  вставках в голову ленты элементы задваиваются или пропадают, а стоимость
  выборки растёт с номером страницы. Курсор содержит `created_at` и `id`,
  размер страницы фиксирован сервером.
- Одна операция `GET /v1/posts` на три ленты: без параметров — по подпискам,
  с `author_id` — лента автора, с `place_geohash` — лента места. Соответствует
  допущению 4, по которому три ленты считаются одним числом.
- Загрузка фотографий двухфазная: `POST /v1/images` возвращает идентификатор
  временного файла, идентификаторы передаются в `POST /v1/posts`, при создании
  файлы переезжают в постоянное хранилище. Невостребованные удаляются.
- API отдаёт ссылки на изображения, байты отдаёт хранилище. Операции чтения
  фотографий учтены в расчёте нагрузки, отдельных методов в спецификации нет.
- Оценка и подписка выражены через `PUT` по адресу, известному заранее:
  подписчик и автор оценки берутся из токена. Повторный запрос идемпотентен,
  что важно при обрывах связи с мобильных.
- Часть методов работает с авторизацией и без неё. Авторизованному
  дополнительно отдаются его оценка поста и признак подписки на автора.
- Выпуск и обновление токена — вне скоупа.
